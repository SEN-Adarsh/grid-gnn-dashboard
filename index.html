    How it works

    Scoring pipeline

    1. Step 1Stored AMI and DT readingsMeter intervals and transformer input measurements
    2. Step 2Causal imputationFills missing intervals using prior available history
    3. Step 3DT power-flow and residualEstimates technical losses and unexplained energy
    4. Step 4Feature engineeringOwn history, DT/peer context, and temporal sequence inputs
    5. Step 5Selected method scoringThe five scoring methods use distinct features and model approaches
    6. Step 6Calibration and thresholdApplies the selected operating point

    Scoring produces two related outputs:

    Ranked meter flags and scoresReview candidates, scores, and reason codes
    DT unexplained-energy balanceTransformer-level residual and daily balance
    1. Step 74-way loss attributionTechnical loss, tamper anomaly, defective/frozen metering, and upstream hooking
    2. Step 8Work-order routingSuggested action, owner, service target, and MIS code
    3. Step 9Response, provenance, and audit logRuntime and internal model/config provenance; score events are logged

    The meter ranking and DT balance are related outputs from shared telemetry and physics features. Loss attribution and work-order fields are heuristic decision-support outputs that require field verification.

    Human review

    Rankings and flags are requests to inspect evidence. They do not trigger enforcement.

    Operating threshold

    The score applies a validation-calibrated precision target. If the target is unattainable, flagging is disabled.

    Attribution limits

    DT loss attribution is a heuristic allocation for review, not verified loss accounting.

    Glossary

    NTL - non-technical loss

    Energy delivered but not billed, including theft, meter faults, or unmetered connections. Technical loss (heat in wires) is estimated separately.

    AT&C losses

    Aggregate Technical & Commercial losses combine technical losses with unbilled or uncollected energy.

    DT - distribution transformer

    The transformer feeding a local low-voltage network. Its measured input supports localization of unexplained energy to the DT.

    AMI - advanced metering infrastructure

    Smart-metering systems report consumption at short intervals. AMI dropout is one of the synthetic demo scenarios.

    PR-AUC (not accuracy)

    Area under the precision–recall curve. We use it because flagged events are rare; accuracy would be misleadingly high for any model that flags nobody.

    p(theft)

    A decision-support score for a meter. It is not a probability of guilt and has not been validated for field use.

    Precision target

    The share of flags that would be justified if inspected, fixed in advance (here 0.70) so thresholds cannot be tuned after seeing results.

    FPR - false positive rate

    How often honest meters get flagged. On honest meter faults the pooled FPR was 47.3% in the recorded run and 46.2% in the reproduced run.

    Data, provenance, and governance

    Data and scope

    The served demo uses the synthetic_india_v2 profile and reference topology. It has no real field-validation claim. Scenario counterfactuals are applied to a copy of the stored demo telemetry.

    The repository contains no customer PII or committed secrets. The IES-aligned design has no central customer-data database. The hosted demonstration uses its packaged synthetic context; utility integrations must keep raw telemetry within the utility-controlled data boundary.

    Inspection decision support

    • The system ranks meters for human review and estimates unexplained energy at DT level.
    • Every flag and suggested work order requires field verification.
    • No automated enforcement action is taken. The system does not determine an offense.
    • Four-way DT attribution and work-order routing are heuristics, not verified loss accounting.

    Model and benchmark limits

    The graph model did not demonstrate a consistent advantage over simpler baselines in the held-out benchmark. The project reports measured performance and limitations without claiming field efficacy or pilot readiness.

    API provenance and audit

    The scoring API returns a configuration hash and a SHA-256 fingerprint for the loaded model; score-event audit records retain both. Score events are written to service storage that is ephemeral across container restarts. The public dashboard does not display or export these values. Its JSON download is a run summary, not an audit filing.
